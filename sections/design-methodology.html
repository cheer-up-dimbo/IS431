3. Design Methodology (Zakir)

This project uses the Pahl and Beitz (Pahl, Beitz, Feldhusen, & Grote, 2007) framework for clarification of task and concept generation, combined with the Systems Engineering V-Model (INCOSE, 2023) to structure decomposition and verification across all system levels.

3.1 Clarification of Task

Insights from the competition study were first translated into specific product requirements using the Product Needs Translation tool (Table 4), which identified important enhancements, performance standards, and user experience objectives. The Function Specifications, which included explicit functions, performance standards, and design justifications for the robot's subsystems (arms, head, legs, body, skeleton, and interface), were subsequently influenced by these translated needs.

The full product needs translation is available in Annex: Product Needs Translation.

3.2 Systems Engineering V-Model

The diagram below presents the V-Model adopted as the guiding design and verification framework for BoxBunny (INCOSE, 2023). The left arm decomposes a subsystem from its concept of operations down to implementation, while the right arm verifies at each corresponding level. Dashed horizontal lines represent traceability: every requirement defined on the left has a pre-defined verification method on the right.

This framework applies at every level of the system. Each of the three subsystems (User Interface, Robot Mechanism, Robot Intelligence) enters the V-Model at Concept of Operations and progresses through its own system requirements, high-level design, detailed design, and implementation. Within Robot Mechanism, the framework is applied again at a finer granularity: each sub-subsystem (Base, Rotation, Height Adjustment, Padding, Arm Actuation) derives its own requirements from the mechanism-level requirements, generates and selects concepts, builds, and verifies independently. The V-Model therefore operates recursively, scaling from the full system down to individual components.

Stage Description BoxBunny Example
Concept of Operations Define the operational context, user needs, and goals for the subsystem For Robot Mechanism: the robot must rotate, adjust height, and deliver punches safely
System Requirements Derive measurable, testable requirements from the concept of operations RM-4: yaw angular velocity of ~150 deg/s; RM-5: 90 deg strike in 0.25 s or less
High-Level Design Decompose into sub-components and define interfaces between them Robot Mechanism splits into Base, Rotation, Height Adjustment, Padding, Arm Actuation
Detailed Design Design each component in full detail: mechanical, electrical, and software Rotation: slewing bearing selection, timing-belt drive sizing, motor mounting
Implementation Fabricate, assemble, and program the physical component or module Machine parts, wire motors, flash firmware
Unit Testing Verify individual components against their detailed design specifications Test motor torque output, sensor accuracy, firmware response time
Subsystem Verification Verify the integrated subsystem against its derived system requirements RM-4 test: measure actual yaw angular velocity of assembled rotation module
System Validation Validate the complete subsystem against original user needs and operational goals User testing: does the robot feel like a realistic sparring partner?
Deployed System Validated and integrated subsystem ready for operation Fully assembled BoxBunny platform deployed in a gym
