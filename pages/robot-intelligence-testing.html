5.3.4 Testing & Validation

The Robot Intelligence subsystem was validated through model performance and interpretability, real-world deployment at the CDE AI Fair, and comprehensive automated testing. This section covers methodology, results, and limitations.

5.3.4.1 Model Validation & Interpretability

This section presents how well the final model performs and provides visual evidence of what the model has learned internally. The goal is to verify that the model is making decisions for the right reasons, not just memorising patterns.

Overall Performance

The deployed model (v11) achieves 96.8% validation accuracy on an unseen person and 94.2% macro F1-score (the average F1 across classes, treating each class equally regardless of size — a fairer measure than accuracy when classes are imbalanced), with only 7 out of 222 samples misclassified. Model v10 reached 97.3% but had poorer live block detection, so v11 was selected for deployment.

Classification Results

The confusion matrix (left) shows exactly where the model gets confused. Each cell represents how often a true punch type (row) was predicted as another type (column). The strong diagonal means the model is correct most of the time. The few off-diagonal cells reveal that errors occur between biomechanically similar punches — for example, left hook confused with left uppercut (both involve the left arm swinging), and block confused with idle (both involve minimal movement).

The per-class accuracy chart (right) shows the hit rate for each punch type individually. Most classes exceed 96%, with right hook and right uppercut achieving perfect 100%. Block is the weakest at 66.7%, and the cause is biomechanical: the start of a block (arms rising from guard into a defensive position) looks almost identical to the start of an uppercut (arms rising into the punch) for the first few frames. This is exactly the failure mode the block annotation fix in 5.3.1 was introduced to address — extending block annotations to cover the full guard sequence (rise, hold, return) so the model learns the entire shape of the action rather than only its onset. Live block reliability improved significantly as a result, even though the validation headline number stayed in the same range.

Training Convergence

The dashboard below tracks how the model improved during training. The loss (top-left) measures how wrong the model's predictions are — lower is better. The accuracy (top-right) shows the percentage of correct predictions on both training data (blue) and unseen validation data (pink). The gap between the two lines indicates overfitting — here the gap stays narrow, confirming the model generalises well rather than memorising training examples. The model reached its best performance at epoch 73 out of 133.

What the Model Learned (t-SNE Visualisation)

To understand what the model has learned internally, its high-dimensional representations (384 dimensions) are compressed to 2D using a technique called t-SNE (t-distributed Stochastic Neighbour Embedding — a dimensionality-reduction method that preserves local similarity, so points close together in the original space stay close in 2D). Each dot represents one punch sample, coloured by its true class. If the model has learned meaningful features, samples of the same punch type should cluster together and different types should be separated. The plot below confirms this — tight, well-separated clusters for each action class. Notably, the clusters that show partial overlap (left hook / left uppercut) match exactly the classes that confuse the model in the confusion matrix above.

Which Frames Matter Most

Gradient saliency (a technique that measures how much the model's output changes with respect to each input, indicating which parts the model relied on most) reveals how much each frame in the 12-frame window contributes to the model's prediction. The chart below shows a clear pattern: later frames are significantly more important than early ones. The most recent frame (index 11) has the highest importance, with frames 6–9 also scoring high. This makes intuitive sense — the most recent motion contains the strongest signal about what punch is being thrown. The first few frames (indices 1–4) contribute less, as they mostly capture the preparation phase before the discriminative motion begins.

5.3.4.2 CDE AI Fair — Real-World Deployment

As introduced in the GUI testing section (5.1), BoxBunny was deployed at the "Robotics Meets AI Showcase" in late January 2025 for public interaction. From a Robot Intelligence perspective, the key context is that the Transformer-based action prediction model was not yet ready — instead, a simpler HSV (Hue-Saturation-Value, a colour space that separates colour from brightness) colour-based glove tracking system was implemented, requiring users to wear red and green gloves. The prototype ran 9 ROS 2 packages with 3 drill modes.

Despite being an earlier, simplified version, the live deployment revealed critical real-world challenges that directly shaped the design of the final system:

Issue Problem Fix in Final System
Background clutter People walking behind the user caused false punch detections Nearest-person tracking prioritises closest and largest person
Colour tracking failure HSV glove tracking susceptible to similarly-coloured objects Replaced with Transformer-based action recognition model
Variable punching stances Fixed velocity thresholds unreliable across users Switched to depth-based proximity detection
LLM cold start Several seconds delay on first coaching prompt Lazy model loading at GUI startup
Touchscreen input friction Typing on 7″ touchscreen awkward with gloves Phone dashboard enables mobile interaction
Camera resource contention Multiple CV consumers each opening camera caused contention Single camera node publishes to shared topics

Table: CDE Fair — real-world issues and fixes that shaped the final system

These lessons directly shaped the final system. Most notably, colour tracking limitations motivated the Transformer-based action recognition model.

5.3.4.8 Limitations

All requirements were met, but several limitations remain:

Limitation Impact Mitigation / Future Work
Block / uppercut onset confusion Block onset (arms rising from guard) is biomechanically similar to uppercut onset in the first few frames → 66.7% on the block class Block annotations extended to include the full hold + return phase to improve live reliability; future work: more varied blocking data from experienced boxers
Glove occlusion Wrist keypoints lost at punch extension Pose dropout augmentation + 12-frame temporal context; fundamental single-camera constraint
Camera viewpoint Model coupled to training camera angle Re-recording required for different viewpoints; fixed mount on robot
Single camera No multi-view triangulation; some punches identical from one angle IMU fusion compensates; multi-camera setup as future work
Jetson thermal Sustained 30fps CV + LLM may cause throttling Adaptive frame rate (~6fps idle) and 20s LLM timeout manage budget
LLM quality 3B model + 128-token cap limits coaching depth Adequate for real-time tips; post-session analysis can be generic
D435i IMU kernel Built-in IMU requires unavailable Tegra kernel module Manual --camera-pitch workaround
