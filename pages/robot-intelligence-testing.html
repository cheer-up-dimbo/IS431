5.3.6 Testing & Validation

The Robot Intelligence subsystem was validated through a combination of real-world deployment testing, automated test suites, and detailed model analysis. This section covers the testing methodology, results, and identified limitations.

5.3.6.1 CDE AI Fair — Real-World Deployment

BoxBunny was deployed as a prototype at the “Robotics Meets AI Showcase” event in late January 2025, where members of the public physically interacted with the robot in a live demonstration setting. This was an earlier, streamlined version of the system running 9 ROS 2 packages with HSV colour-based glove tracking and 3 training drill modes (Reaction Time, Shadow Sparring, Defence).

The showcase revealed several real-world challenges that directly informed the design of the final system:

Table: CDE Fair Issues and Fixes
Issue Problem Fix in Final System
Background clutter People walking behind the user caused false punch detections Nearest-person tracking algorithm prioritises closest and largest person
Colour tracking failure HSV glove tracking susceptible to similarly-coloured objects in the environment Replaced entirely with Transformer-based action recognition model
Variable punching stances Fixed velocity thresholds unreliable across different users Switched to depth-based proximity detection (hand approaching camera)
LLM cold start Several seconds delay on first coaching prompt Lazy model loading at GUI startup instead of first prompt
Touchscreen input friction Typing questions on 7″ touchscreen awkward — users had to bend down Phone dashboard enables mobile interaction from user's own device
Camera resource contention Multiple CV consumers each opening camera caused contention Single camera node publishes to shared topics that all consumers subscribe to

These real-world deployment lessons directly shaped the final BoxBunny system — most notably, the colour tracking limitations motivated the entire development of the Transformer-based action recognition model that became the core of the final system.

5.3.6.2 Testing Infrastructure

Testing followed a bottom-up strategy: unit tests validate individual components, integration tests verify cross-module communication, and system-level testing uses hardware simulation and operational notebooks. In total: 146 pytest unit tests, 28 integration tests, and a 12-section master notebook covering the full operational test workflow.

5.3.6.3 Key Unit Tests

The 146 unit tests are organised across 3 test files with 12 shared pytest fixtures. The most critical test categories are highlighted below (full breakdown available in the Appendix):

Sensor Fusion — 44 tests (test_punch_fusion.py)

  • Ring buffer operations (7 tests): maxlen eviction, time-based expiry, pop_match behaviour
  • Pad-constraint filtering (10 tests): validates that each punch type is only accepted on biomechanically valid pads (e.g., jab only on centre pad, left hook only on left pad)
  • Reclassification (8 tests): verifies secondary prediction fallback when primary prediction violates pad constraints
  • Defence classification (8 tests): validates priority ordering (HIT > BLOCK > SLIP > DODGE > UNKNOWN)

Gamification — 30 tests (test_gamification.py)

  • Rank system (10 tests): all 6 tiers from Novice to Elite, boundary conditions, XP calculations
  • Session XP (7 tests): base XP per mode, completion bonus, difficulty multiplier, streak bonus
  • Achievements (5 tests): unlock conditions, duplicate prevention

Database — 45+ tests (test_database.py)

  • User management (13 tests): CRUD operations, password verification, duplicate prevention
  • Pattern lock (5 tests): SHA-256 hashing, set/verify/overwrite
  • Session persistence (8 tests): save/retrieve, mode filtering, event logging
  • Gamification persistence (7 tests): XP tracking, rank progression, personal records

Run command: python3 -m pytest tests/ -v

5.3.6.4 Integration Testing

28 cross-module tests (notebooks/scripts/test_integration.py) validate:

  • Configuration loading and YAML validation across all config files
  • Pad-location constraint mapping correctness (punch type → pad validity matrix)
  • CV + IMU fusion algorithm end-to-end (temporal matching, reclassification)
  • All 21 ROS message field verification (every custom message type has correct fields)
  • Motor protocol validation (punch codes 1–6 map correctly to motor commands)
  • Reaction time detection logic

Run command: python3 notebooks/scripts/test_integration.py

5.3.6.5 System-Level Testing

Teensy Simulator

A GUI-based simulator that emulates the Teensy 4.1 microcontroller with 6 IMU sensors (4 pad sensors + 2 arm sensors), enabling complete system testing without physical hardware. The simulator supports manual mode (click buttons to inject individual pad impacts with configurable force levels) and auto mode (execute predefined punch sequences for reproducible testing). Preset configurations allow different test scenarios to be saved and replayed.

Used in development mode: ros2 launch boxbunny_core boxbunny_dev.launch.py

5.3.6.6 Model Validation & Interpretability

Overall Performance

The deployed model (v11) achieves 96.8% validation accuracy on an unseen person, 94.2% macro F1-score, with only 7 out of 222 validation samples misclassified. The best accuracy model (v10) reached 97.3% but had poorer live block detection, leading to v11 being selected for deployment.

Confusion Matrix

Most errors occur between biomechanically similar punch types — left hook confused with left uppercut, and block confused with idle. Block has the lowest per-class accuracy at 66.7% due to having only 6 validation samples (the smallest class).

Per-Class Accuracy

Right hook and right uppercut achieve 100%, cross 98.1%, jab 96.4%, left hook 96.0%, left uppercut 91.7%, idle 100%, block 66.7%.

Training Convergence

A 2×2 dashboard showing loss, accuracy, learning rate schedule, and train-val accuracy gap across 133 epochs. The model converged at epoch 73 with minimal overfitting, validated by the narrow gap between training and validation accuracy throughout.

t-SNE Embeddings

The model's learned 384-dimensional sequence embeddings, projected to 2D via t-SNE, show tight, well-separated clusters for each action class. This confirms the model has learned discriminative features rather than memorising training data. Notably, the clusters that show partial overlap (e.g., left hook and left uppercut) correspond exactly to the highest off-diagonal values in the confusion matrix.

Attention Heatmaps

Per-layer attention weights across the 4 Transformer layers reveal meaningful temporal learning: early layers focus on local temporal patterns (attending primarily to nearby frames), while later layers develop broader attention spans covering the full 12-frame window. This progression from local to global temporal reasoning demonstrates that the Transformer is learning hierarchical temporal representations, not simply averaging.

5.3.6.8 Limitations

While all requirements were met, several limitations remain:

  • Block class underrepresentation: With only 6 validation samples, block accuracy (66.7%) is the weakest class. More training data from varied blocking styles would improve this.
  • Glove occlusion: Heavy boxing gloves occlude YOLO wrist keypoint detection at punch extension — the exact moment when detection matters most. Mitigated by pose dropout augmentation and temporal context (12 frames outvotes 2–3 bad frames), but remains a fundamental constraint of single-camera 2D pose estimation.
  • Camera viewpoint sensitivity: The model is tightly coupled to the camera angle used during training. Different viewpoints require re-recording and re-annotating the entire dataset, as models do not generalise across viewpoints.
  • Single camera: No multi-view triangulation. Some punches appear identical from a single forward-facing viewpoint.
  • Jetson thermal constraints: Sustained high-load sessions (30fps CV + LLM generation) may cause thermal throttling. Adaptive frame rate and LLM timeout (20s) help manage the thermal budget.
  • LLM generation quality: The 3B parameter model with a 128-token generation cap limits coaching depth. Adequate for real-time 1–2 sentence tips, but post-session analysis occasionally produces generic advice.
  • D435i IMU kernel: The RealSense D435i's built-in IMU requires the hid_sensor_hub kernel module, which is unavailable on the Jetson's Tegra kernel. Manual camera pitch configuration (--camera-pitch) is used as a workaround.
