5.3.4 Testing & Validation

The Robot Intelligence subsystem was validated through real-world deployment, automated test suites, and detailed model analysis. This section covers methodology, results, and limitations.

5.3.4.1 CDE AI Fair — Real-World Deployment

BoxBunny was deployed at the "Robotics Meets AI Showcase" in late January 2025. Members of the public physically interacted with the robot in a live setting. This earlier version ran 9 ROS 2 packages with HSV colour-based glove tracking and 3 drill modes.

The showcase revealed real-world challenges that directly shaped the final system:

Table: CDE Fair Issues and Fixes
Issue Problem Fix in Final System
Background clutter People walking behind the user caused false punch detections Nearest-person tracking prioritises closest and largest person
Colour tracking failure HSV glove tracking susceptible to similarly-coloured objects Replaced with Transformer-based action recognition model
Variable punching stances Fixed velocity thresholds unreliable across users Switched to depth-based proximity detection
LLM cold start Several seconds delay on first coaching prompt Lazy model loading at GUI startup
Touchscreen input friction Typing on 7″ touchscreen awkward with gloves Phone dashboard enables mobile interaction
Camera resource contention Multiple CV consumers each opening camera caused contention Single camera node publishes to shared topics

These lessons directly shaped the final system. Most notably, colour tracking limitations motivated the Transformer-based action recognition model.

5.3.4.2 Testing Infrastructure

Testing followed a bottom-up strategy: unit tests validate individual components, integration tests verify cross-module communication, and system-level testing uses hardware simulation. Totals: 146 pytest unit tests, 28 integration tests, and a 12-section master notebook for the full operational workflow.

5.3.4.3 Key Unit Tests

146 unit tests across 3 files with 12 shared pytest fixtures. Key categories highlighted below (full breakdown in the Appendix):

Sensor Fusion — 44 tests (test_punch_fusion.py)

  • Ring buffer operations (7): maxlen eviction, time-based expiry, pop_match
  • Pad-constraint filtering (10): each punch type accepted only on valid pads
  • Reclassification (8): secondary prediction fallback on pad constraint violations
  • Defence classification (8): priority ordering (HIT > BLOCK > SLIP > DODGE > UNKNOWN)

Gamification — 30 tests (test_gamification.py)

  • Rank system (10): all 6 tiers, boundary conditions, XP calculations
  • Session XP (7): base XP per mode, completion bonus, difficulty multiplier, streak
  • Achievements (5): unlock conditions, duplicate prevention

Database — 45+ tests (test_database.py)

  • User management (13): CRUD, password verification, duplicate prevention
  • Pattern lock (5): SHA-256 hashing, set/verify/overwrite
  • Session persistence (8): save/retrieve, mode filtering, event logging
  • Gamification persistence (7): XP tracking, rank progression, personal records

Run command: python3 -m pytest tests/ -v

5.3.4.4 Integration Testing

28 cross-module tests (notebooks/scripts/test_integration.py) validate:

  • Configuration loading and YAML validation across all config files
  • Pad-location constraint mapping (punch type → pad validity matrix)
  • CV + IMU fusion end-to-end (temporal matching, reclassification)
  • All 21 ROS message field verification
  • Motor protocol validation (punch codes 1–6 → motor commands)
  • Reaction time detection logic

Run command: python3 notebooks/scripts/test_integration.py

5.3.4.5 System-Level Testing

Teensy Simulator

A GUI-based simulator emulating the Teensy 4.1 with 6 IMU sensors (4 pad + 2 arm), enabling full system testing without physical hardware. Supports manual mode (click to inject pad impacts with configurable force) and auto mode (predefined punch sequences for reproducible testing).

Used in development mode: ros2 launch boxbunny_core boxbunny_dev.launch.py

Teensy Simulator in action — injecting pad impacts and observing system response

Master Notebook (boxbunny_runner.ipynb)

A 12-section Jupyter notebook serving as the primary operational testing orchestrator:

  1. Build & Setup — colcon build, dependency check
  2. Unit Tests — run full 146-test pytest suite
  3. System Check — hardware verification (camera, CUDA, models, database)
  4. Launch System — start all ROS 2 nodes + Teensy simulator + GUI
  5. Stop System — graceful shutdown
  6. GUI Test — visual inspection of all 24 pages
  7. Phone Dashboard — start server + public tunnel + QR code
  8. CV Model Live Test — camera feed with pose skeleton + action label overlay
  9. LLM Coach Test — interactive AI coach chat GUI
  10. Build Vue Frontend — rebuild SPA after changes
  11. Sound Test — play all 18 audio effects
  12. Demo Profiles & Benchmarks — user cards + percentile rankings

Launch Configurations

  • boxbunny_dev.launch.py — Development mode with Teensy simulator (no hardware needed)
  • boxbunny_full.launch.py — Production mode with real hardware

5.3.4.6 Model Validation & Interpretability

This section presents how well the final model performs and provides visual evidence of what the model has learned internally. The goal is to verify that the model is making decisions for the right reasons, not just memorising patterns.

Overall Performance

The deployed model (v11) achieves 96.8% validation accuracy on an unseen person and 94.2% macro F1-score, with only 7 out of 222 samples misclassified. Model v10 reached 97.3% but had poorer live block detection, so v11 was selected for deployment.

Classification Results

The confusion matrix (left) shows exactly where the model gets confused. Each cell represents how often a true punch type (row) was predicted as another type (column). The strong diagonal means the model is correct most of the time. The few off-diagonal cells reveal that errors occur between biomechanically similar punches — for example, left hook confused with left uppercut (both involve the left arm swinging), and block confused with idle (both involve minimal movement).

The per-class accuracy chart (right) shows the hit rate for each punch type individually. Most classes exceed 96%, with right hook and right uppercut achieving perfect 100%. Block is the weakest at 66.7%, primarily because it had only 6 validation samples — meaning just 2 misclassifications drop it significantly. Collecting more block samples would likely improve this.

Training Convergence

The dashboard below tracks how the model improved during training. The loss (top-left) measures how wrong the model's predictions are — lower is better. The accuracy (top-right) shows the percentage of correct predictions on both training data (blue) and unseen validation data (pink). The gap between the two lines indicates overfitting — here the gap stays narrow, confirming the model generalises well rather than memorising training examples. The model reached its best performance at epoch 73 out of 133.

What the Model Learned (t-SNE Visualisation)

To understand what the model has learned internally, its high-dimensional representations (384 dimensions) are compressed to 2D using a technique called t-SNE. Each dot represents one punch sample, coloured by its true class. If the model has learned meaningful features, samples of the same punch type should cluster together and different types should be separated. The plot below confirms this — tight, well-separated clusters for each action class. Notably, the clusters that show partial overlap (left hook / left uppercut) match exactly the classes that confuse the model in the confusion matrix above.

Temporal Attention Patterns

The model uses a Transformer architecture that decides how much attention to pay to each frame in the 12-frame input window. The heatmaps below show these attention patterns across the 4 Transformer layers. Early layers (left) focus on nearby frames — the model first looks at local motion. Later layers (right) attend across the full window — combining local cues into a broader understanding of the full punch trajectory. This progression from local to global attention is a hallmark of effective temporal learning and confirms the model is reasoning about motion sequences, not just reacting to individual frames.

5.3.4.8 Limitations

All requirements were met, but several limitations remain:

  • Block class underrepresentation: Only 6 validation samples yield 66.7% accuracy. More varied blocking data would improve this.
  • Glove occlusion: Heavy gloves occlude YOLO wrist keypoints at punch extension. Mitigated by pose dropout augmentation and 12-frame temporal context, but remains a fundamental single-camera constraint.
  • Camera viewpoint sensitivity: The model is tightly coupled to its training camera angle. Different viewpoints require re-recording the entire dataset.
  • Single camera: No multi-view triangulation. Some punches appear identical from one viewpoint.
  • Jetson thermal constraints: Sustained high-load sessions (30fps CV + LLM) may cause throttling. Adaptive frame rate and LLM timeout (20s) manage the thermal budget.
  • LLM generation quality: The 3B model with 128-token cap limits coaching depth. Adequate for real-time tips, but post-session analysis can be generic.
  • D435i IMU kernel: The RealSense D435i's built-in IMU requires hid_sensor_hub, unavailable on Jetson's Tegra kernel. Manual --camera-pitch is used as a workaround.
