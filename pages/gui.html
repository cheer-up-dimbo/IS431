5. User Interface (GUI) (Zakir)

The GUI is the control centre of the BoxBunny system. As described in Section 4.2, the user journey from login to active training involves selecting a mode, configuring parameters, and starting a session, all while wearing boxing gloves. This context shaped the core design principle for the interface: simplicity first. A complicated interface undermines the training experience, so the goal was to keep the system as transparent as possible. The user should be thinking about boxing, not about navigating software. Every design decision in this chapter follows from that principle.

5.1. Design Specifications

The design specifications for the GUI were derived from the hardware constraints of the target platform and the usability needs identified through the user journey in Section 4.2. The guiding principle was that the interface should never become the obstacle. If a user has to stop and think about how to navigate to the next screen mid-session, the design has already failed.

Hardware Constraints

The GUI runs on an NVIDIA Jetson Nano 4GB paired with a 7-inch touchscreen at 1024x600 resolution, running Ubuntu 20.04 LTS. These are fixed constraints inherited from the overall system design. The display size, resolution, and available memory are not adjustable, so every layout and performance decision had to account for these boundaries from the start. Designs that worked on a standard laptop screen had to be re-evaluated against what would actually render correctly on a 7-inch display held at arm's length during a training session.

5.2. Concept Generation and Evaluation

Before any implementation work began, three design decisions required concept generation and evaluation: the development framework, the navigation architecture, and the data storage approach. Each decision had direct consequences for the usability, maintainability, and feasibility of the final system. The options considered for each are documented below.

Framework Selection

The project had a four-month development window from December 2024 to April 2025. The chosen framework needed to run on the Jetson Nano without additional configuration, support touchscreen interaction natively, and be learnable quickly enough to leave adequate time for actual feature development. Four options were evaluated against these criteria.

PySide6 was selected. It runs natively on the Jetson Nano, has mature support for touchscreen layouts, and builds on existing Python knowledge which reduced the time spent on framework setup. The extensive Qt documentation and active community support also lowered the risk of hitting unresolvable technical blockers within the compressed timeline.

Navigation Architecture

Three navigation paradigms were evaluated against the core requirement that any feature must be reachable within a small number of interactions from the main menu, and that the interface must remain usable with boxing gloves on.

The hierarchical page stack was selected. Beyond its usability advantages, this approach also naturally models how a boxing training session is structured: the user makes a series of sequential choices to configure a session, trains, and then reviews results. The navigation stack implementation meant that the back button behaviour was handled centrally rather than being manually coded on each individual page, which kept the codebase clean as the number of pages grew.

Data Storage

Because multiple users share a single BoxBunny unit, a data isolation strategy was needed to ensure that each user's training history remained private and separate. Three strategies were evaluated.

A per-user database file approach was selected. Each user's data is stored under their own directory in two SQLite files: one for combination training progress and one for performance test results. This also simplified account management considerably, since adding or removing a user account is as simple as creating or deleting their folder.

Feature Prioritisation

With a fixed timeline and a broad feature set, MoSCoW prioritisation was applied to determine what would be built first and what would be deferred. The goal was to ensure that the core training functionality was stable and tested before any enhanced features were attempted.

Must Have features were targeted in the first three iterations. Should Have features followed once the foundation was confirmed stable. Could Have features were built where time permitted. Features in the Will Not Have category were recorded explicitly to prevent scope creep during development.

5.3. Detailed Design

With the framework, navigation model, and data strategy selected, the detailed design focused on translating these decisions into a working system architecture. The key design challenge was structuring the codebase so that GUI development could proceed independently of hardware availability, since the computer vision and robotic arm subsystems were being developed in parallel by other team members.

System Architecture

The GUI is structured across five distinct layers, each with a clearly defined responsibility. This separation ensures that changes in one layer, such as swapping the database engine or updating the hardware communication protocol, do not cascade into unrelated parts of the codebase. 

+----------------------------------------------------------+
|        Presentation Layer (PySide6 Widgets)              |
|  - All pages, buttons, labels, and input fields          |
|  - Event callbacks and user-facing animations            |
+----------------------------------------------------------+
|              Application Layer                           |
|  - Navigation stack and page history                     |
|  - User session state and configuration                  |
+----------------------------------------------------------+
|             Business Logic Layer                         |
|  - Combo Curriculum Engine                               |
|  - Performance Testing Logic                             |
|  - User Management                                       |
+----------------------------------------------------------+
|            Integration Layer                             |
|  - Arduino serial communication                          |
|  - Computer vision interface (file-based handshake)      |
|  - Robot control interface                               |
+----------------------------------------------------------+
|              Data Layer                                  |
|  - SQLite databases (per-user files)                     |
|  - Configuration file management                         |
+----------------------------------------------------------+

The Integration Layer is worth highlighting specifically. Rather than letting the GUI call hardware interfaces directly, all hardware communication is routed through this layer. During development on a Windows laptop with no hardware connected, the Integration Layer switches automatically to mock interfaces that simulate hardware responses. This allowed the full GUI to be built and tested before any physical hardware was available, which was essential given the parallel development timelines across the team.

5.4. Implementation and Testing

The GUI was built over six iterations across the four-month development window, following the iterative prototyping approach outlined in Chapter 3. Each iteration had a defined objective, produced working and testable software, and closed with a structured review before the next iteration began. This approach was chosen deliberately because it surfaced integration issues early, when they were still contained, rather than allowing them to compound into larger problems later in the timeline.

Several issues only became apparent during testing within an iteration rather than during design. A database schema mismatch between two different score scales caused constraint violations that required the database to be rebuilt with corrected constraints. A back button that consistently returned to the wrong page regardless of how the user arrived was resolved by the navigation stack, which tracked entry paths automatically. A discrepancy between session counts in the CSV file and combo attempt counts in the database was resolved by resetting the CSV history during migration to the per-user database structure. Each of these was caught and resolved within the iteration that introduced it.

5.5. Evaluation and Outcomes

The evaluation assessed whether the GUI met the design specifications established in Section 5.1 and the broader project deliverables. The primary design principle, that the interface should never become the obstacle, was used as the lens for assessing outcomes. The status of all core deliverables is detailed in the table below.

All core requirements were met. The navigation stack resolved the back button consistency issue that surfaced during early iterations. The per-user database structure confirmed zero data mixing across test accounts. Startup and page transition times measured well within acceptable bounds on the Jetson Nano hardware. The interface remained readable and navigable during active training sessions, which validated the core usability decisions made in Section 5.2.

Limitations and Future Work

Two areas were not fully resolved within the project timeline. The computer vision integration currently runs through a file-based handshake rather than a direct API call, as the CV subsystem and GUI were developed in parallel without a stable shared interface being finalised before the submission deadline. Additionally, the AI coaching feature in the combo training mode falls back to hardcoded responses when the language model is unavailable, which will occur on hardware with insufficient memory. Both are documented as priority items for the next development phase.
