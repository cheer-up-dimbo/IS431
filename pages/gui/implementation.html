Implementation

The GUI was built over six iterations across 15 weeks (December 2024 to April 2025). Each iteration had a defined objective, produced working software, and closed with a review before the next iteration began. This section documents the development timeline, the system architecture, and the key engineering decisions that shaped the final system.

Development Iterations

Several issues only surfaced during testing rather than during design. A database schema mismatch between two different score scales (0 to 1 versus 0 to 5) caused CHECK constraint violations, requiring the database to be rebuilt with corrected constraints. A back button that always returned to the same page regardless of entry path was resolved by implementing the navigation stack in Iteration 5. A discrepancy between session counts in a CSV file and combo attempt counts in the database was resolved by resetting the CSV history during migration to the per-user database structure. Each of these was caught and fixed within the iteration that introduced it.

System Architecture

The application follows a five-layer architecture. Each layer has a single responsibility, so changes in one layer do not cascade into unrelated parts of the codebase. 

+----------------------------------------------------------+
|        Presentation Layer (PySide6 Widgets)              |
|  All pages, buttons, labels, input fields                |
|  Event callbacks, visual feedback                        |
+----------------------------------------------------------+
|              Application Layer                           |
|  Navigation stack and page history                       |
|  User session state, configuration                       |
+----------------------------------------------------------+
|             Business Logic Layer                         |
|  Combo Curriculum Engine (mastery algorithm)             |
|  Performance Testing Logic                               |
|  User Management, Proficiency Assessment                 |
+----------------------------------------------------------+
|            Integration Layer                             |
|  Arduino serial communication (multi-mode)               |
|  Computer vision interface (file-based handshake)        |
|  Robot arm control interface (ROS topics / serial)       |
+----------------------------------------------------------+
|              Data Layer                                  |
|  SQLite databases (per-user files)                       |
|  Configuration file management                           |
+----------------------------------------------------------+

The Integration Layer is the critical enabler for parallel development. Rather than calling hardware interfaces directly, all hardware communication is routed through this layer. During development on a Windows laptop with no hardware connected, the layer switches automatically to mock interfaces that simulate hardware responses. This allowed the full GUI to be built and tested before any physical hardware was available. When deployed on the Jetson Nano, the mock interfaces are replaced by real implementations without any changes to the layers above.

Key Engineering Decisions

Navigation Stack

The application contains over 40 pages managed by a central QStackedWidget. Rather than coding back button destinations manually on each page, a navigation stack records the current page index before every transition. The navigate_to() method pushes the current index onto the stack, and navigate_back() pops from it. If the stack is empty, the system falls back to the main menu. This eliminated an entire category of navigation bugs as the page count grew.

Proficiency Assessment

On signup, new users complete a six-question checklist covering boxing experience, training frequency, familiarity with combinations, comfort with sparring, and fitness level. Each answer maps to a numeric weight. The total score maps the user to Beginner, Intermediate, or Advanced, with an option to override the suggestion. This classification gates access to Sparring mode (Intermediate and Advanced only) and determines the default combo difficulty tier shown on the training page.

Combo Curriculum and Mastery Algorithm

The curriculum contains 50 combinations: 15 Beginner, 20 Intermediate, and 15 Advanced. Each combo uses a notation system where numbers 1 through 6 represent punch types (Jab, Cross, Lead Hook, Rear Hook, Lead Uppercut, Rear Uppercut), with a "b" suffix for body shots and text labels for defensive movements (slip, block, roll). A combo is considered mastered when the user has completed at least five sessions with an average score of 3.0 or above. Progress is tracked per-user in the SQLite database and persists across sessions.

Sparring Mode: Markov Chain Generation

Sparring mode generates punch sequences using a first-order Markov chain. Transition probabilities are biased by the user's weakness profile, so the robot produces more of the punch types and transitions that the user has historically scored lowest on. This creates a training experience that adapts to the individual user without requiring explicit difficulty settings. Access is restricted to Intermediate and Advanced users through the proficiency classification.

AI Coaching Integration

The combo training flow includes a post-session chat page where users can ask for feedback on their performance. The chat is powered by a local LLM (Qwen 2.5 3B GGUF via llama-cpp-python). On hardware where the model cannot be loaded (insufficient memory or missing model file), the system falls back to hardcoded template responses. This fallback was implemented as a design decision rather than an error state, since the Jetson Nano's 4 GB of RAM makes model availability uncertain.
