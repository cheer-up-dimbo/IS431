Implementation

The GUI was built over six iterations across 15 weeks (December 2024 to April 2025). Each iteration had a defined objective, produced working software, and closed with a review before the next iteration began. This section documents the development timeline, the system architecture, and the key engineering decisions that shaped the final system.

Development Iterations

System Architecture

The application follows a five-layer architecture. Each layer has a single responsibility, so changes in one layer do not cascade into unrelated parts of the codebase.

Presentation Layer

PySide6 widgets: all pages, buttons, labels, input fields, event callbacks, visual feedback

Application Layer

Navigation stack and page history, user session state, configuration management

Business Logic Layer

Combo Curriculum Engine (mastery algorithm), Performance Testing Logic, User Management, Proficiency Assessment

Integration Layer

GuiBridge (ROS 2 QThread bridge), CV interface (ROS topics + file-based fallback), Robot arm control (ROS command topics), Phone dashboard (shared SQLite + JSON command file)

Data Layer

SQLite databases (per-user files), configuration file management

The Integration Layer is the critical enabler for parallel development. Rather than calling hardware interfaces directly, all hardware communication is routed through this layer. During development on a Windows laptop with no hardware connected, the layer switches automatically to mock interfaces that simulate hardware responses. When deployed on the Jetson Nano, the mock interfaces are replaced by real implementations without any changes to the layers above.

ROS 2 Integration

The GUI communicates with the broader BoxBunny system through a GuiBridge class that spawns a background QThread running a ROS 2 node. ROS topic callbacks on the worker thread emit Qt Signals, which are automatically marshalled to the GUI's main thread for safe widget updates. This architecture allows real-time punch confirmations, drill progress updates, session state changes, and coaching tips to flow into the interface without blocking the UI event loop.

When ROS 2 is unavailable (for example, during UI development on a laptop without the full robotics stack), the bridge degrades gracefully: all signals are suppressed, service calls return failure immediately, and the GUI runs in standalone mode using mock interfaces. This preserved the ability to develop and test the entire GUI independently of hardware throughout the project.

IMU Navigation

A key usability constraint identified during needs finding is that boxers cannot reliably operate a touchscreen while wearing gloves. Research on touch input shows that even moderate hand coverage significantly reduces accuracy on targets below 48px (Parhi, Karlson and Myers, 2006). The GUI addresses casual gloved interaction by using 60px minimum touch targets throughout, but the more complete solution for in-session use is hands-free navigation via the robot's IMU pads.

The four pads double as navigation controls outside of training sessions. Left pad moves to the previous item, right pad moves to the next, centre pad confirms a selection, and head pad navigates back. This mapping follows the directional convention familiar from physical four-button controllers, which reduces the need for users to learn new interaction patterns (Norman, 2013).

One edge case is the home screen, which has no parent to return to. On the home screen, the head pad opens a quick-access preset overlay instead of attempting a back navigation with nowhere to go.

During active training, all pad navigation is disabled. Without this, punch impacts on the pads would trigger accidental page changes mid-session. The disable state activates during the countdown and active phases of every session and restores automatically during rest and after session completion.

Session Orchestration

The GUI is the session lifecycle controller for every training mode: technique drills, sparring, free training, and performance tests. Every session begins with an explicit start request from the GUI and ends with an explicit end request that retrieves the session summary.

The sequence on a typical session is as follows. The user configures the session and taps Start. The GUI sends a request to the backend with the training mode, difficulty, and username, and receives a session ID in return. Throughout the session, state changes arrive from the backend — countdown, active round, rest period, next round — and the GUI uses these to drive the on-screen timer, round counter, and screen transitions. When the final round ends or the user exits early, the GUI sends an end request with the session ID. The backend returns a summary containing punch counts, accuracy scores, and performance metrics, which the results page then displays.

This separation means Section 5.3 (Robot Intelligence) handles all scoring and data collection logic, while Section 5.1 (GUI) handles all presentation and user flow logic. The GUI does not need to know how punch scoring is calculated, and the backend does not need to know how results are displayed.

Phone Dashboard

A companion web dashboard was implemented to give users access to their training data from their phone. The dashboard is a Vue 3 single-page application served by a lightweight backend running on the same Jetson. Users connect to the robot's WiFi access point and open the dashboard in their phone browser.

The dashboard reads from the same SQLite databases as the touchscreen GUI, providing a synchronized view of session history, performance trends, achievement progress, and combo mastery. Users can also start training sessions remotely, adjust robot height, manage presets, and chat with the AI coach. Remote commands are written as JSON to a shared file that the GUI polls every 100 ms, providing near-instant responsiveness without requiring a direct socket connection between the dashboard and the GUI process. The backend implementation of the dashboard server, API endpoints, and WebSocket communication is documented in Section 5.3 (Robot Intelligence).

Gamification System

A gamification layer was added to sustain user motivation across sessions. Experience points (XP) are awarded per training session based on the training mode, session completion percentage, performance score, and current training streak. Users progress through six ranks: Novice, Contender, Fighter, Warrior, Champion, and Elite, each requiring increasing XP thresholds.

Twelve achievement badges track specific milestones such as first completed session (First Blood), 100 total punches (Century), fastest reaction time (Speed Demon), and highest defense rate (Iron Chin). A daily training streak counter encourages consistency, with bonus XP multipliers applied during active streaks. Personal records for power, stamina, and reaction metrics are tracked and surfaced on the dashboard. The session history interface consolidating all training types is shown in Appendix 3.

Combo Curriculum and Mastery Algorithm

The curriculum contains 50 combinations: 15 Beginner, 20 Intermediate, and 15 Advanced. Each combo uses a notation system where numbers 1 through 6 represent punch types (Jab, Cross, Lead Hook, Rear Hook, Lead Uppercut, Rear Uppercut), with a "b" suffix for body shots and text labels for defensive movements (slip, block, roll). A combo is considered mastered when the user has completed at least five sessions with an average score of 3.0 out of 5.0 or above. Progress is tracked per-user in the SQLite database and persists across sessions. The self-select sequence builder interface is shown in Appendix 3.

Sparring Mode: Markov Chain Generation

Sparring mode generates punch sequences using a first-order Markov chain. Each boxing style (Pressure Fighter, Counter Puncher, Infighter, Out-Boxer, Random) defines a transition probability matrix over punch types. Starting from a "start" state, the system picks the next punch based on weighted probabilities, continuing until an "end" state is reached or a safety limit of six punches per combo is hit. Sparring is available to all proficiency levels. The style selection interface is shown in Appendix 3.

Below is the transition matrix for the Counter Puncher style as an example. Each row shows the current state, and the columns show the probability of transitioning to each next punch (or ending the combo).

Worked example (Counter Puncher):

1. start: Roll probabilities. Jab (0.30), Cross (0.30), End (0.40). Suppose the roll picks Jab.
2. After Jab: Cross (0.40), End (0.60). Suppose the roll picks Cross.
3. After Cross: Lead Hook (0.30), Rear Hook (0.20), End (0.50). Suppose the roll picks End.

Result: the generated combo is 1-2 (Jab, Cross). The Counter Puncher style has high "end" probabilities, so it naturally produces short, precise combinations. Contrast this with the Pressure Fighter, whose low "end" probabilities generate longer, more aggressive sequences.

When a user's weakness profile is available (from previous sparring sessions), the transition weights are blended with a bias multiplier. The blending factor alpha increases gradually with session count (capped at 0.4), so the adaptation strengthens over time without fully overriding the style's character.

AI Coaching Integration

Immediate, specific feedback is a consistent predictor of skill acquisition in motor learning (Schmidt and Lee, 2011). The GUI surfaces AI coaching feedback at two points in the session flow to support this.

During training, coaching tips appear in a bar that slides down from the top of the active session screen. The bar is color-coded by tip type: technique corrections, encouragement, drill suggestions, and general boxing guidance are visually distinguished. The bar auto-dismisses after ten seconds to avoid obscuring the combo display during active punching.

After a session, the results page includes a chat interface where users can ask the AI coach for specific feedback. The coach has access to the session summary, including which combos were missed, accuracy by punch type, and session duration. When the local LLM is unavailable due to memory constraints, the GUI falls back to a pool of 54 categorised hardcoded tips rather than showing an error. A relevant templated response is a better experience than no response at all (Norman, 2013). The LLM model, prompt engineering, and inference pipeline are documented in Section 5.3 (Robot Intelligence).

Sound System

Audio feedback reinforces task events without requiring the user's visual attention, which is useful during active training when the user is focused on the pads rather than the screen (Gaver, 1989). The GUI uses 18 WAV sound effects, all preloaded at startup for zero-latency playback.

A priority tier system prevents lower-priority sounds from masking higher-priority ones. Round start and end bells carry the highest priority among session sounds. Countdown ticks sit below bells, hit confirmation sounds sit below ticks, and UI navigation clicks sit at the lowest priority. A navigation click cannot interrupt a bell, but a bell will always cut through regardless of what else is playing. Volume and per-sound toggles are available from the Settings page.
