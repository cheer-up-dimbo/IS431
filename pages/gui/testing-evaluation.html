Testing and Evaluation

After completing all six iterations, a structured validation pass was conducted across the full feature set. This section presents the functional testing results, performance measurements, user testing observations, and the limitations that remain.

Functional Testing

Functional testing verified that every feature behaved correctly under normal use conditions. Test scenarios covered user authentication, combo curriculum progression, performance test instrumentation, navigation stack correctness, and multi-user data isolation.

All functional tests passed. The navigation stack test is worth highlighting: the scenario traced a five-page deep navigation path and verified that pressing back four times returned through each page in the correct reverse order. This confirmed that the centralised stack implementation handled arbitrary navigation depth correctly.

Performance Testing

Performance testing verified that the GUI remained responsive within the Jetson Nano's hardware constraints. Quantitative targets were defined prior to implementation and measured after the final iteration.

All performance targets were met with significant margin. The most constrained metric was Arduino sensor data latency at 320 ms average, which still sat 36% below the 500 ms ceiling. Memory usage at 180 MB left substantial headroom on the Jetson Nano's 4 GB, which is important because other subsystems (computer vision, robot control) also consume memory when running concurrently.

User Testing: Robotics and AI in Work and Play Event

Members of the public physically interacted with BoxBunny at the "Robotics and AI in Work and Play" event. Two displays were available during the demonstration: the original 7-inch touchscreen mounted directly on the robot, and a larger external monitor connected to the same Jetson Nano showing the same GUI output.

During the session, participants and observers consistently gravitated toward the larger monitor when reading data analytics, reviewing training results, and navigating between pages. Users who attempted to operate the 7-inch screen during active training reported difficulty reading combo prompts and performance statistics at arm's length. Several participants noted that the text was too small to follow comfortably while also focusing on punching technique. Users who switched to the larger monitor did not report the same issues.

These observations validated a hardware revision. The 7-inch display was replaced with a 10.1-inch IPS capacitive touchscreen (1280x800 resolution, DSI interface). The upgrade improved text legibility and made the analytics pages significantly easier to read during and after training. Because the GUI used proportional layout sizing rather than fixed pixel coordinates, the existing interface scaled to the new resolution without requiring a redesign cycle. The compressed timeline meant this change is framed as a hardware revision informed by direct user observation, not a full iterative software redesign.

Limitations

Two integration points were not fully resolved within the project timeline. The computer vision subsystem communicates with the GUI through a file-based handshake rather than a direct API call. This was a consequence of the CV and GUI subsystems being developed in parallel without a stable shared interface being finalised before the submission deadline. The mechanism works reliably but introduces unnecessary file I/O overhead that a direct function call would avoid.

The AI coaching feature in the combo training mode falls back to hardcoded template responses when the language model is unavailable. On the Jetson Nano's 4 GB RAM, loading the Qwen 2.5 3B model alongside the GUI and other subsystems is not always feasible. The fallback was designed as a graceful degradation rather than a failure, but it does limit the personalisation of coaching feedback on memory-constrained hardware.

The display upgrade to 10.1 inches occurred late in the project. While the interface scaled correctly to the new resolution, there was no opportunity to conduct a second round of structured user testing on the new hardware. The improvement in readability is based on qualitative observation during the event rather than controlled measurement.

Finally, the GUI was developed by a single team member. All design decisions, implementation, and testing were conducted by one person over 15 weeks. This compressed timeline meant that certain features classified as "Could Have" in the MoSCoW analysis (progress charts, customisable training programs, data export) were either partially implemented or deferred entirely.
