5.2.4 Padding — Troubleshooting & Iteration

V-Model Traceability: Both defects span the Electrical → Firmware → Application boundary and directly affect RM-6 strike detection reliability. They are cross-referenced on the Arm Actuation Troubleshooting page as Defects 7 and 8.

Two cross-layer defects directly affect the padding subsystem's IMU sensing pipeline. Both were identified during integration testing and resolved through firmware and application-level fixes.

Defect 7: I²C Bus Hang

Layer Firmware (Electrical → Software boundary)
Symptom MPU6050 holds SDA permanently low, freezing the entire I²C bus
Root Cause Long (30–40 cm) unshielded jumper wires introduce parasitic capacitance. At 400 kHz, the "Repeated Start" condition can lock the MPU6050's internal state machine
Resolution Hard STOP protocol — endTransmission(true) after every register write, forcing a full STOP + START sequence. Adds ~20 µs latency per read but eliminates the bus-hang failure mode
Status ✅ Resolved

Root-Cause Analysis

The MPU6050 implements I²C with an internal state machine that tracks bus conditions. When the master issues a Repeated Start (SR) — pulling SDA low while SCL is high without an intervening STOP — the sensor must detect the transition within a narrow timing window (tHD;STA ≥ 0.6 µs per the I²C spec). On short PCB traces (< 5 cm), this timing is comfortably met.

However, the BoxBunny padding assembly routes 30–40 cm 4-conductor jumper wires from each IMU breakout to the Teensy 4.1. At this length, parasitic capacitance (≈ 50–100 pF per wire) introduces RC rise-time delays on both SDA and SCL. At 400 kHz Fast Mode, these delays can cause the MPU6050's state machine to misinterpret the Repeated Start as a data bit, latching SDA low indefinitely. Because the four IMUs are distributed across the Teensy 4.0's two hardware I²C buses (Wire / Wire1), a latch on either bus freezes that bus's sensing pipeline.

The fix replaces all Repeated Start sequences with a Hard STOP + full START sequence (endTransmission(true)). The STOP condition unambiguously resets the MPU6050's state machine regardless of parasitic capacitance, because it only requires SDA to transition high (pulled by the 4.7 kΩ resistor) while SCL is high — a condition that is reliably achieved even with slow edges.

Performance penalty: The Hard STOP protocol adds ~20 µs per read cycle (one STOP + one START vs one SR). At 200 Hz scan rate across 4 IMUs, this totals ~16 ms additional overhead per second (< 2% of the 5 ms loop budget) — an acceptable trade-off for guaranteed bus stability.

Defect 8: Nyquist Blind-Spot in Strike Detection

Layer Application (GUI software)
Symptom Visible acceleration peaks in plot exceed threshold, but system fails to register strike events
Root Cause GUI refreshes at 20 Hz (50 ms), but punch impulses last ~30 ms. Naïve "check latest sample" approach samples only 1 of ~10 accumulated data points per frame, missing inter-frame strikes
Resolution Scan-window peak detection: np.max(mag_arr[-n_scan:]) scans all accumulated samples since last GUI tick (n_scan ≈ 10 at 200 Hz firmware / 20 Hz GUI)
Status ✅ Resolved

Root-Cause Analysis

The IMU firmware publishes accelerometer data at 200 Hz (5 ms sample period) via the /motor_feedback ROS 2 topic. The GUI (unified_GUI_V3.py) processes this data in its Qt event loop, which runs at 20 Hz (50 ms tick period). Between each GUI tick, approximately 10 IMU samples accumulate in the subscription buffer.

The original strike detection logic checked only the most recent sample at each GUI tick: 

# BEFORE (broken): checks only 1 of ~10 samples
if mag_arr[-1] > threshold:
    publish_strike_event()

A punch impulse lasts approximately 20–30 ms. If the peak occurs between two GUI ticks — at sample index 4 of 10, for example — the latest sample (index 10) may already be below the threshold. The peak is visible in the real-time plot (which renders all buffered samples) but invisible to the point-in-time threshold check.

The fix scans all accumulated samples since the last tick: 

# AFTER (fixed): scans all samples in the window
n_scan = max(1, int(firmware_hz / gui_hz))  # ≈ 10
peak = np.max(mag_arr[-n_scan:])
if peak > threshold:
    publish_strike_event(zone=np.argmax(...))

This guarantees that any impulse exceeding the threshold within the 50 ms window is detected, regardless of when within the window it occurs.
