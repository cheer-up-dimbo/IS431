Firmware & Software Architecture

This section documents the two-tier control architecture, the Teensy 4.0 firmware evolution, the PyQt5 GUI, and the Dynamic Sparring FSM combat engine.

Two-Tier Hierarchical Architecture

The control system follows a two-tier design with all FSM intelligence on the PC/Jetson side:

  • Tier 1 — Jetson Orin NX (ROS 2 Humble): Hosts the GUI (unified_GUI_V3.py), publishes motor commands at 100 Hz, and performs all combat FSM decision-making, strike sequencing, and impact detection.
  • Tier 2 — Teensy 4.0 (Micro-ROS): Executes a deterministic 200 Hz unified loop (5 ms). Each cycle performs CAN motor control, I2C IMU polling, MDDS10 height PWM/DIR, and publishes a 21-double feedback payload via micro-ROS.

The Teensy firmware evolved through four major versions:

Version Key Change
V3 CAN motor control + MDDS10 height, sparse edge-trigger
V4 Merged IMU I2C polling into 200 Hz loop; 21-double feedback payload
V4.1 I2C Hard STOP protocol fix for long-wire bus hang
V4.2 Micro-ROS disconnect recovery via SCB_AIRCR hardware reset

Feedback Payload Structure (V4)

The /motor_feedback topic carries a Float64MultiArray of 21 doubles: 

[pos×4, current×4, CAN_count, IMU_accel×12]
 ─────  ────────   ─────────  ──────────────
  0-3     4-7          8         9-20

The 12 IMU fields carry raw 3-axis acceleration (X, Y, Z) from up to 4 MPU6050 sensors.

Strike Library

Each strike in the library is defined by exactly two motor-space nodes: a Windup position and an Apex (impact) position. The operator records these using a live encoder Teach Pendant:

  1. Disarm the motors — the arm is freely movable by hand.
  2. Position the arm at the desired windup position; click Record Windup. The raw encoder values are captured.
  3. Position the arm at the apex; click Record Apex.
  4. The GUI dynamically computes the recovery position using proportional snap-back.

Strike libraries are saved and loaded as JSON files containing both left and right arm data: 

{
  "left":  { "Jab": {"windup": [...], "apex": [...]}, ... },
  "right": { "Right Hook": {"windup": [...], "apex": [...]}, ... }
}

Dynamic Sparring Finite State Machine

The Dynamic Sparring FSM replaces the original discrete, return-to-zero action queue with a continuous-state machine that chains strikes fluidly from the arm's last physical position.

Vector Alignment Skip Logic

When a new strike is triggered, the FSM evaluates the angular alignment between the intended strike vector and the actual approach vector:

θalign = cos−1(Vstrike · Vapproach / |Vstrike| · |Vapproach|)    (Eq. 15)

  • θ < threshold (default 30°) → skip windup — approach is already aligned.
  • θ ≥ threshold → windup required — skipping would change the strike's character.

M1-Based Perimeter Transit Routing

When a windup is required, a direct path may cross the robot's centre-line (user's body zone). The transit router inserts intermediate via-points — library windups whose Motor 1 (Roll) position falls between the current and target M1 — sorted in the direction of travel. This forces the arm to orbit along the perimeter.

Synchronized Per-Motor Speed Scaling

To prevent curved trajectories when motors travel different distances, the FSM computes individual speeds so both arrive simultaneously:

spdmi = vbase × Δmi / max(Δm1, Δm2)    (Eq. 16)

A 0.5 rad/s minimum floor prevents motor stalling when one axis barely needs to move.

Proportional Snap-Back Recovery

precovery = papex − λ · (papex − pwindup)    (Eq. 14)

Where λ ∈ [0.1, 1.0] is the snap-back factor (operator slider). This eliminates the need for a manually taught third point.

FSM Decision Pipeline

Strike Triggered
  │
  ├─ Compute alignment angle θ
  │
  ├─ θ < threshold? ──→ YES: Skip Windup → Command Apex directly
  │
  └─ θ ≥ threshold? ──→ NO: Windup Required
                              ├─ Compute M1-based transit waypoints
                              ├─ Route through intermediate windups
                              ├─ Command target Windup
                              └─ Command Apex
  │
  └─ Calculate Dynamic Snap-Back → Command Recovery (synced speeds)

Topic Function

Dynamic Speed Adaptation

When enabled, the system estimates joint-space travel distance and computes the required speed to complete the movement within the allocated duration:

veff = min(max(vbase, dtotal/(T − 0.3)), vmax)    (Eq. 17)
