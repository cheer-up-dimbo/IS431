5.3.4 Intelligent Behaviour & Control

This section covers the intelligent systems that enable BoxBunny to perceive, decide, and act in real time — from sensor fusion and inference to adaptive sparring and AI coaching.

5.3.4.1 CV + IMU Sensor Fusion

The punch_processor node bridges perception and confirmed action by fusing computer vision predictions with IMU pad impact data.

Fusion Algorithm

When an IMU pad impact is detected (acceleration exceeding 5.0 m/s² after gravity calibration), the node queries the CV prediction ring buffer within a ±500ms temporal window. Frame-count voting selects the dominant prediction type (most frames, not highest confidence), and the result is emitted as a ConfirmedPunch with both CV confidence and IMU force data.

Pad-Constraint Filtering

Each pad accepts only biomechanically valid punch types:

  • Centre pad — jab and cross only
  • Left pad — left hook and left uppercut only
  • Right pad — right hook and right uppercut only
  • Head pad — any punch type

If the primary CV prediction violates the constraint, secondary predictions are checked with a minimum confidence threshold of 0.25.

Fallbacks

CV-only mode: ≥3 consecutive frames at ≥0.6 confidence, emitted with a 0.3 penalty — ensures punches are still registered even if the IMU sensor fails.
IMU-only mode: default 0.3 confidence, punch type inferred from pad location — ensures punches are still registered even if the camera feed is degraded.
These fallback paths ensure the system degrades gracefully if either sensor fails.

5.3.4.2 Real-Time Inference Pipeline

TensorRT Deployment

Both the YOLO Pose model and the action recognition transformer are optimised with TensorRT FP16 on the Jetson Orin Nano.

FPS Sensitivity

The voxel temporal features use 2-frame (67ms) and 8-frame (267ms) lookback deltas computed at 30fps. If the frame rate drops, these deltas span different real-world time intervals, degrading classification accuracy. This sensitivity drove the TensorRT optimisation work — ensuring the pipeline consistently meets the 33ms per-frame budget.

Offline → Live Inference Gap

A major engineering challenge was that models performing well on pre-recorded clips struggled in live deployment. Four specific issues were identified and solved:

  1. Processing bottleneck — voxel extraction and YOLO inference were sequential, causing the model to receive stale feature windows. Fix: parallelised into separate worker threads.
  2. Frame buffer issues — dropped frames created temporal discontinuities in the rolling window. Fix: implemented a proper RollingFeatureBuffer with FIFO queue and strict frame ordering.
  3. YOLO as bottleneck — PyTorch YOLO consumed most of the 33ms frame budget on Jetson. Fix: converted YOLO to a TensorRT engine (.engine format), dramatically reducing inference time.
  4. Effective FPS mismatch — the model was trained at consistent 30fps but the live pipeline ran at variable rates. Fix: TensorRT optimisation of both models guaranteed consistent throughput.

Latency Breakdown

Component Latency Notes
YOLO Pose (TensorRT) ~16ms On GPU, single frame
Depth → voxel extraction ~10ms Background subtraction + voxelisation
YOLO + voxel in parallel ~16ms Separate threads, limited by slower
Model forward pass ~8ms 730K trainable params, d=192
Total per frame ~24ms 42fps theoretical, 30fps practical

Post-Processing

Raw model outputs pass through three stages: EMA smoothing (α=0.35) to reduce frame-to-frame jitter, a hysteresis gate (12% confidence margin) to prevent oscillation between classes, and a state machine requiring minimum 2 frames to enter an action, minimum 3 frames hold, sustain confidence ≥0.78, with block requiring 4 consecutive frames.

Adaptive Frame Rate

The cv_node runs at 30fps during active training sessions but drops to ~6fps when the session is idle, freeing GPU headroom for LLM inference during rest periods.

GPU Memory Management

TensorRT action model (~200MB) + TensorRT YOLO (~150MB) + Qwen2.5-3B LLM (~2GB) + frame buffers (~100MB) = ~2.5GB simultaneous, comfortably within the 8GB shared LPDDR5 memory.

5.3.4.3 AI Sparring Engine

Five AI opponent styles are implemented as Markov chain transition matrices, each with distinct behavioural profiles:

Style Behaviour Profile
Boxer Technical, balanced. Mixes all punch types with clean transitions, moderate attack frequency.
Brawler Aggressive, predictable. Heavy on hooks and crosses, short gaps between attacks.
Counter-Puncher Reactive, patient. Low base attack frequency, spikes after user punches with quick jab/cross counters.
Pressure Relentless, overwhelming. Very high frequency, minimal gaps, all punch types. Tests defensive endurance.
Switch Unpredictable. Rotates between the other 4 styles every ~20 seconds. Requires continuous adaptation.

Difficulty Scaling (3 levels)

Parameter Easy Medium Hard
Attack interval 2.0s 1.2s 0.7s
Counter-punch probability 30% 50% 80%
Arm speed 8 rad/s 15 rad/s 25 rad/s

Weakness Tracking

The sparring_weakness_profile table persistently tracks per-punch-type defence success rates across sessions. The AI biases its attacks toward punch types where the user has the lowest defence rate, forcing continuous improvement on weak areas.

Free Training Mode

A pad-to-counter mapping (centre pad → jab/cross, left pad → left hooks/uppercuts, right pad → right hooks/uppercuts, head pad → jab/cross) with a 300ms counter cooldown and 5-second idle guard return provides reactive, unstructured practice.

5.3.4.4 LLM Coach — Architecture & Tuning

Model

Qwen2.5-3B-Instruct (instruction-tuned for following coaching prompts), quantised to GGUF Q4_K_M (~2GB), running via llama-cpp-python with full GPU offload (n_gpu_layers=-1). Inference typically completes in 0.5–2 seconds with a 2048-token context window and 128-token generation limit.

System Prompt Design

A 24-line embedded system prompt in llm_node.py instructs the model to:

  • Act as "BoxBunny AI Coach" with AIBA manual knowledge
  • Know all 6 punch types and their codes (1=jab through 6=right uppercut)
  • Understand 5 boxing styles (European, Russian, American, Cuban, hybrid)
  • Adjust advice to the user's skill level (beginner/intermediate/advanced)
  • Keep real-time tips to 1–2 sentences
  • Output plain text only (no markdown formatting)

Different system prompt keys are used for different contexts: real-time coaching tips during active sessions, post-session analysis, and interactive chat.

Tuning Interface

A standalone PySide6 chat GUI (llm_chat_gui.py) was built specifically for iterative prompt tuning during development. It features streaming token display (showing text appearing word by word), model selection from a configuration file, configurable system prompts, full conversation history, and sentence completion mode. This tool was used extensively to refine the coaching prompt wording and test coaching quality across different session contexts.

Boxing Knowledge Base

17 documents in data/boxing_knowledge/ across 8 categories, sourced from the official AIBA Coaches Manual (AIBA, 2015), the APB Professional Coaches Manual (AIBA, 2017), plus custom-written documentation covering technique descriptions (jab, cross, hooks, uppercuts, stance and guard), defensive manuals (blocking, parrying, slipping, footwork), combination progressions (beginner to advanced), 8-week training programmes, conditioning guides, and common mistakes. An additional comprehensive knowledge base (boxing_knowledge.txt, 100+ lines) covers orthodox stance, all punch mechanics, defensive techniques, and AIBA training stages. This knowledge is injected into the LLM context during coaching analysis for sport-specific terminology and methodology.

Preventing Cut-Off Responses

Several mechanisms ensure complete responses: short max_tokens (128) to stay within budget, explicit system prompt instruction ("keep tips SHORT — 1–2 sentences"), 20-second inference timeout with hard thread termination, markdown stripping (**bold**, *italic*, # headers), and sentence completion detection.

Fallback System

65 pre-written tips in 4 categories (technique, encouragement, correction, suggestion) are used when the LLM is unavailable, the model file is missing, GPU runs out of memory, or inference times out. The system tracks consecutive failures and attempts a model reload after 3 consecutive failures.

5.3.4.5 Session Management

The session_manager node orchestrates the entire training session lifecycle through a 5-state machine:

States

IDLE → COUNTDOWN (3 seconds) → ACTIVE → REST → COMPLETE → auto-reset to IDLE (3 seconds).

Per-State Side Effects

Each state transition triggers coordinated changes across all nodes:

State Behaviour
IDLE IMU in navigation mode, CV at ~6fps, robot disabled
COUNTDOWN IMU switches to training mode (200ms grace period), auto-height adjustment (once), round start signal to robot
ACTIVE CV at 30fps, data collection active (ConfirmedPunch, DefenseEvent, UserTracking logged), autosave every 10 seconds
REST IMU maintained in training mode, CV drops to idle rate, data collection pauses
COMPLETE Final save to per-user SQLite database, publish SessionPunchSummary (20+ fields covering punch distribution, force, movement, defence, sensor pipeline statistics), auto-reset to IDLE

Round cycling is fully configurable: default 3 rounds × 180 seconds work + 60 seconds rest. Concurrent session protection forces a reset if StartSession is called while not in IDLE state.
