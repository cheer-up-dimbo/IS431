5.3.2 Intelligent Behaviour & Control

All intelligent behaviour runs as a network of ROS 2 Humble nodes on the Jetson, communicating via custom message types and services. Each subsection below corresponds to one or more ROS nodes that handle a specific aspect of the system — from fusing sensor data to generating AI coaching tips. Together they form the decision-making layer between the CV perception pipeline (Section 5.3.1) and the dashboard and analytics layer (Section 5.3.3).

5.3.2.1 CV + IMU Sensor Fusion

The punch_processor node fuses computer vision predictions with IMU pad impact data to produce confirmed punch events.

Fusion Algorithm

When an IMU pad impact exceeds 5.0 m/s² (after gravity calibration), the node queries the CV prediction ring buffer within a ±500ms window. Frame-count voting selects the dominant prediction type, and the result is emitted as a confirmed punch with both CV confidence and IMU force data.

Pad-Constraint Filtering

Each pad accepts only biomechanically valid punch types:

  • Centre pad — jab and cross only
  • Left pad — left hook and left uppercut only
  • Right pad — right hook and right uppercut only
  • Head pad — any punch type

If the primary CV prediction violates the constraint, secondary predictions are checked with a minimum confidence threshold of 0.25.

Fallbacks

CV-only mode: ≥3 consecutive frames at ≥0.6 confidence, emitted with a 0.3 penalty.
IMU-only mode: default 0.3 confidence, punch type inferred from pad location.
These fallback paths ensure graceful degradation if either sensor fails.

5.3.2.2 Real-Time Inference Pipeline

FPS Sensitivity — Why 30fps Matters

The action prediction model was trained on features extracted at a consistent 30fps. Its voxel temporal deltas use 2-frame (67ms) and 8-frame (267ms) lookbacks — if the actual frame rate drops below 30fps, these deltas span different real-world time intervals than what the model learned, causing the model to misclassify punches. In other words, the action model's accuracy is directly tied to maintaining 30fps — even a small drop degrades predictions significantly.

The YOLO Bottleneck — TensorRT Conversion

The single biggest deployment challenge was the YOLO Pose model. Running in its default PyTorch format (.pt) on the Jetson, YOLO alone consumed most of the 33ms per-frame budget, dragging the entire pipeline below 30fps. Because YOLO provides the pose features that the action model depends on, this bottleneck meant the action model was receiving features at inconsistent, lower frame rates — making it inaccurate despite performing well on pre-recorded 30fps data.

Converting YOLO to a TensorRT engine (.engine format with FP16 precision) resolved this completely. TensorRT optimises the model's computation graph for the Jetson's GPU architecture, fusing operations and eliminating overhead. This brought YOLO inference down to ~16ms, well within the 33ms frame budget, allowing the full pipeline to sustain a consistent 30fps. The action model immediately became accurate and reliable in live deployment once this conversion was done — confirming that the accuracy issue was never the model itself, but the inconsistent frame rate feeding it.

Offline → Live Inference Gap

Beyond the YOLO bottleneck, three additional issues were solved to bridge the gap between offline accuracy and live performance:

  1. Sequential processing — voxel extraction and YOLO ran one after the other, doubling per-frame time. Fix: parallelised into separate worker threads so they run concurrently.
  2. Frame buffer discontinuities — dropped frames created gaps in the temporal window. Fix: proper rolling feature buffer with FIFO queue and strict frame ordering.
  3. Effective FPS mismatch — trained at consistent 30fps but live pipeline ran at variable rates. Fix: TensorRT optimisation of both YOLO and the action model guaranteed consistent throughput.

Latency Breakdown

Component Latency Notes
YOLO Pose (TensorRT) ~16ms On GPU, single frame
Depth → voxel extraction ~10ms Background subtraction + voxelisation
YOLO + voxel in parallel ~16ms Separate threads, limited by slower
Model forward pass ~8ms 730K trainable params, d=192
Total per frame ~24ms 42fps theoretical, 30fps practical

Post-Processing

Raw outputs pass through three stages: EMA smoothing (α=0.35) to reduce frame-to-frame jitter, a hysteresis gate (12% confidence margin) to prevent class oscillation, and a state machine requiring minimum 2 frames to enter an action, minimum 3 frames hold, sustain confidence ≥0.78, with block requiring 4 consecutive frames.

Adaptive Frame Rate

The cv_node runs at 30fps during active sessions but drops to ~6fps when idle, freeing GPU headroom for LLM inference during rest periods.

5.3.2.3 AI Sparring Engine

The sparring system generates intelligent, adaptive robot behaviour during training sessions. Five AI opponent styles are implemented as Markov chain transition matrices, each producing distinct attack patterns:

Style Behaviour Profile
Boxer Technical, balanced. Mixes all punch types with clean transitions, moderate attack frequency.
Brawler Aggressive, predictable. Heavy on hooks and crosses, short gaps between attacks.
Counter-Puncher Reactive, patient. Low base attack frequency, spikes after user punches with quick jab/cross counters.
Pressure Relentless, overwhelming. Very high frequency, minimal gaps, all punch types. Tests defensive endurance.
Switch Unpredictable. Rotates between the other 4 styles every ~20 seconds. Requires continuous adaptation.

Difficulty Scaling (3 levels)

Parameter Easy Medium Hard
Attack interval 2.0s 1.2s 0.7s
Counter-punch probability 30% 50% 80%
Arm speed 8 rad/s 15 rad/s 25 rad/s

Weakness Tracking

The sparring_weakness_profile table persistently tracks per-punch-type defence success rates across sessions. The AI biases attacks toward punch types where the user has the lowest defence rate, forcing continuous improvement on weak areas.

The user-facing sparring experience (style selection, session configuration, and results display) is covered in the GUI section (5.1). This section focuses on the underlying intelligence that drives the robot's behaviour.

Defence Detection

When the robot attacks during sparring, the system must determine how the user responded. Each robot punch opens a 500ms detection window, during which the punch_processor classifies the user's response using a priority-based system:

Priority Response Detection Method
1 Hit Arm IMU detects physical contact — the robot's punch landed
2 Block CV model detects block pose (confidence ≥ 0.3)
3 Slip Large displacement — user's bounding box moved ≥40px laterally or ≥0.15m in depth
4 Dodge Moderate displacement — ≥20px laterally or ≥0.08m in depth
5 Unknown No detectable response within the 500ms window

Defence results feed into the sparring analytics (defence rate, breakdown by type) and the weakness tracking system, which uses them to target the user's weakest areas in future sessions.

Free Training Mode

An unstructured practice mode where the robot reacts to the user's punches rather than following a scripted sequence. When the user hits a pad, the robot responds with a contextually appropriate counter-punch:

User Hits Robot Responds With
Centre pad Jab or Cross
Left pad Left Hook or Left Uppercut
Right pad Right Hook or Right Uppercut
Head pad Jab or Cross

A 300ms cooldown prevents rapid-fire counters, and the robot returns to guard position after 5 seconds of inactivity.

5.3.2.4 LLM Coach

A local AI coach runs entirely on the Jetson — no cloud, no internet — providing personalised boxing guidance in three modes: real-time tips during training, post-session analysis, and interactive chat via the phone dashboard.

Why Local LLM?

Cloud-based AI coaching would add network latency and require stable internet — neither is guaranteed in a gym environment. Running the LLM on-device ensures instant responses, zero dependency on external services, and complete privacy of training data. The challenge was fitting a capable language model alongside the CV pipeline within the Jetson's 16GB shared memory.

Model Selection & Deployment

Model Qwen2.5-3B-Instruct — chosen for instruction-following ability at small size
Quantisation GGUF Q4_K_M (~2GB) — fits alongside CV models in shared GPU memory
Runtime llama-cpp-python with full GPU offload
Response time 0.5–2 seconds per response
Context window 2,048 tokens
Generation limit 128 tokens (prevents cut-off mid-sentence)

Three Coaching Modes

Mode When What It Does
Real-time tips Every ~18 seconds during active rounds 1–2 sentence coaching tips based on recent punches, combo progress, and session stats. Displayed on the GUI's CoachTipBar widget.
Post-session analysis After session completes 2–3 paragraph detailed analysis referencing specific metrics (punch count, power trends, weak areas). Can suggest specific drills via structured tags.
Interactive chat Anytime via phone dashboard Full conversation with the AI coach. Users can ask technique questions, request training plans, or get explanations of their stats. Word-by-word streaming display.

The system also includes personality modes to keep interactions engaging — an advice mode for motivational pep talks and encouragement, and a Singlish mode that responds in Singaporean colloquial English, adding local flavour to the coaching experience. These modes are selectable via the chat interface and demonstrate the flexibility of the system prompt approach.

System Prompt Design

A 24-line embedded system prompt instructs the model to act as "BoxBunny AI Coach" with knowledge of all 6 punch types and their codes, 5 boxing styles (European, Russian, American, Cuban, hybrid), and AIBA methodology. The prompt enforces plain text output (no markdown formatting) and adjusts advice depth to the user's skill level (beginner/intermediate/advanced). Different system prompt keys are used for each of the three coaching modes.

Inference Parameters & Tuning

The following parameters were tuned during development to balance response quality, speed, and coherence:

Parameter Value Why This Value
Temperature 0.7 Balances variety with coherence — lower values produced repetitive tips, higher values caused off-topic responses
Max tokens 128 Keeps real-time tips to 1–2 sentences — prevents mid-sentence cut-offs within the generation budget
Context window 2,048 Large enough to fit system prompt + session stats + knowledge base context without exceeding memory
GPU layers All (-1) Full GPU offload for fastest inference — CPU fallback too slow for real-time tips
Inference timeout 20s If inference hangs (GPU contention, model issue), the system serves a fallback tip instead of waiting indefinitely

A standalone PySide6 chat GUI (llm_chat_gui.py) was built for iterative prompt tuning. It supports streaming token display, model selection, configurable system prompts, and sentence completion detection — used extensively to refine coaching quality before deployment.

Boxing Knowledge Base

To ground the LLM's responses in real boxing expertise, 17 documents are injected into its context during coaching analysis:

Category Docs Content
Techniques 5 Jab, cross, hooks, uppercuts, stance & guard
Defence 3 Blocking, slipping, footwork
Combinations 3 Beginner to advanced progressions
Training plans 2 8-week beginner & intermediate programmes
Other 4 Conditioning, common mistakes, coaching, FAQ
Official references 2 AIBA Coaches Manual (2015), APB Manual (2017)

Reliability & Fallback

Several mechanisms ensure the coach never fails silently:

  • Response quality — 128-token limit prevents cut-offs, explicit "keep tips SHORT" instruction, markdown stripping removes formatting artifacts
  • Timeout protection — 20-second hard timeout on a background thread prevents the coach from blocking the system
  • Fallback tips — 65 pre-written tips across 4 categories (technique, encouragement, correction, suggestion) are served when the LLM is unavailable, the model file is missing, or GPU memory runs out
  • Auto-recovery — the system tracks consecutive failures and attempts a model reload after 3 failures in a row
