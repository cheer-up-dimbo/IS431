5.3.4 Intelligent Behaviour & Control

This section covers the intelligent systems that enable BoxBunny to perceive, decide, and act in real time — from sensor fusion and inference to adaptive sparring and AI coaching.

5.3.4.1 CV + IMU Sensor Fusion

The punch_processor node fuses computer vision predictions with IMU pad impact data to produce confirmed punch events.

Fusion Algorithm

When an IMU pad impact exceeds 5.0 m/s² (after gravity calibration), the node queries the CV prediction ring buffer within a ±500ms window. Frame-count voting selects the dominant prediction type, and the result is emitted as a confirmed punch with both CV confidence and IMU force data.

Pad-Constraint Filtering

Each pad accepts only biomechanically valid punch types:

  • Centre pad — jab and cross only
  • Left pad — left hook and left uppercut only
  • Right pad — right hook and right uppercut only
  • Head pad — any punch type

If the primary CV prediction violates the constraint, secondary predictions are checked with a minimum confidence threshold of 0.25.

Fallbacks

CV-only mode: ≥3 consecutive frames at ≥0.6 confidence, emitted with a 0.3 penalty.
IMU-only mode: default 0.3 confidence, punch type inferred from pad location.
These fallback paths ensure graceful degradation if either sensor fails.

5.3.4.2 Real-Time Inference Pipeline

TensorRT Deployment

Both the YOLO Pose model and the action recognition transformer are optimised with TensorRT FP16 on the Jetson Orin Nano.

FPS Sensitivity

Voxel temporal features use 2-frame (67ms) and 8-frame (267ms) lookback deltas at 30fps. If the frame rate drops, these deltas span different real-world intervals, degrading accuracy. This drove the TensorRT optimisation work — ensuring the pipeline meets the 33ms per-frame budget.

Offline → Live Inference Gap

Models performing well on pre-recorded clips struggled in live deployment. Four issues were identified and solved:

  1. Processing bottleneck — voxel extraction and YOLO inference were sequential, causing stale feature windows. Fix: parallelised into separate worker threads.
  2. Frame buffer issues — dropped frames created temporal discontinuities. Fix: implemented a proper rolling feature buffer with FIFO queue and strict frame ordering.
  3. YOLO as bottleneck — PyTorch YOLO consumed most of the 33ms budget on Jetson. Fix: converted to a TensorRT engine, dramatically reducing inference time.
  4. Effective FPS mismatch — trained at consistent 30fps but live pipeline ran at variable rates. Fix: TensorRT optimisation of both models guaranteed consistent throughput.

Post-Processing

Raw outputs pass through three stages: EMA smoothing (α=0.35) to reduce frame-to-frame jitter, a hysteresis gate (12% confidence margin) to prevent class oscillation, and a state machine requiring minimum 2 frames to enter an action, minimum 3 frames hold, sustain confidence ≥0.78, with block requiring 4 consecutive frames.

Adaptive Frame Rate

The cv_node runs at 30fps during active sessions but drops to ~6fps when idle, freeing GPU headroom for LLM inference during rest periods.

5.3.4.3 AI Sparring Engine

Five AI opponent styles are implemented as Markov chain transition matrices, each with distinct behavioural profiles:

Style Behaviour Profile
Boxer Technical, balanced. Mixes all punch types with clean transitions, moderate attack frequency.
Brawler Aggressive, predictable. Heavy on hooks and crosses, short gaps between attacks.
Counter-Puncher Reactive, patient. Low base attack frequency, spikes after user punches with quick jab/cross counters.
Pressure Relentless, overwhelming. Very high frequency, minimal gaps, all punch types. Tests defensive endurance.
Switch Unpredictable. Rotates between the other 4 styles every ~20 seconds. Requires continuous adaptation.

Difficulty Scaling (3 levels)

Parameter Easy Medium Hard
Attack interval 2.0s 1.2s 0.7s
Counter-punch probability 30% 50% 80%
Arm speed 8 rad/s 15 rad/s 25 rad/s

Weakness Tracking

The sparring_weakness_profile table persistently tracks per-punch-type defence success rates across sessions. The AI biases attacks toward punch types where the user has the lowest defence rate, forcing continuous improvement on weak areas.

A free training mode provides reactive, unstructured practice via a pad-to-counter mapping (centre pad → jab/cross, left pad → left hooks/uppercuts, right pad → right hooks/uppercuts, head pad → jab/cross) with a 300ms counter cooldown and 5-second idle guard return.

5.3.4.4 LLM Coach

Model & Deployment

Qwen2.5-3B-Instruct, quantised to GGUF Q4_K_M (~2GB), running via llama-cpp-python with full GPU offload. Inference completes in 0.5–2 seconds with a 2048-token context window and 128-token generation limit.

System Prompt & Coaching Modes

A 24-line embedded system prompt instructs the model to act as "BoxBunny AI Coach" with knowledge of all 6 punch types, 5 boxing styles, and AIBA methodology. Tips are kept to 1–2 sentences in plain text. Three prompt keys serve different contexts: real-time tips during active rounds, post-session analysis, and interactive chat.

A standalone PySide6 chat GUI was built for iterative prompt tuning during development, featuring streaming token display, model selection, and conversation history.

Boxing Knowledge Base

17 documents sourced from official AIBA manuals plus custom-written content, injected into the LLM context for sport-specific terminology:

Category Documents Source
Techniques 5 Jab, cross, hooks, uppercuts, stance
Defence 3 Blocking, slipping, footwork
Combinations 3 Beginner to advanced progressions
Training Plans 2 8-week programmes
Other 4 Conditioning, mistakes, coaching, FAQ
Reference 2 AIBA Coaches Manual, APB Manual

Reliability

Short max_tokens (128), explicit brevity instructions, a 20-second inference timeout, and markdown stripping ensure complete, clean responses. When the LLM is unavailable or times out, 65 pre-written tips across 4 categories (technique, encouragement, correction, suggestion) are served instead. The system attempts a model reload after 3 consecutive failures.
