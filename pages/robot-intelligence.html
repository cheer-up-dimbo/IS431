5.3 Robot Intelligence (Yogeeswaran)

Robot Intelligence is the AI brain that turns BoxBunny from a static striking target into an adaptive sparring partner. It sees what the boxer is doing in real time, decides how the robot should respond, drives the LLM coach that gives feedback, and surfaces every session as analytics on a phone dashboard.

At its core is a computer vision pipeline that classifies 8 punch types using depth-based 3D voxel motion fused with 2D pose estimation. A ROS 2 workspace on an NVIDIA Jetson Orin NX orchestrates that perception output alongside IMU sensing, an adaptive sparring engine, and a local Qwen2.5-3B LLM coach, with everything running on-device, no cloud, no internet required.

Requirements and Design Considerations

These requirements were derived from the Function Analysis, user journey, and the physical constraints of deploying real-time computer vision on an embedded platform during live boxing training.

ID Requirement Rationale
RI-1 Classify 8 boxing actions in real-time at >=30 FPS Match human defensive reaction speed; voxel temporal features depend on consistent 30fps frame intervals
RI-2 End-to-end latency (camera to motor command) <=150ms Matches average intermediate boxer defensive reaction time
RI-3 Classification accuracy >=90% on unseen person validation set Reduce false triggers and incorrect counter-punches during live sparring
RI-4 CV + IMU sensor fusion for confirmed punch events Single-source detection unreliable; fusion eliminates false positives from camera noise and accidental pad contacts
RI-5 All inference on-device (NVIDIA Jetson Orin NX 16 GB), no cloud Gym WiFi unreliable; latency budget prohibits cloud round-trip; zero internet requirement
RI-6 Multiple adaptive AI sparring styles with weakness tracking Prevent user habituation; support varied training objectives
RI-7 Real-time coaching feedback via local LLM Personalized technique guidance without cloud dependency

System Design Narrative

Following the Systems Engineering V-Model in Section 3.2, RI-1 to RI-7 were fixed before any model architecture, ROS node, or LLM prompt was written (INCOSE, 2023). These requirements trace back to the product needs mapped in Appendix 6. The diagram below applies the same V-Model structure used in Robot Mechanism (5.2) and GUI (5.1), but tailored to the engineering decisions specific to a real-time AI subsystem: model design, sensor fusion, on-device LLM deployment, and live verification.

In product terms, the Robot Intelligence layer had to feel like a sparring partner that understood what the user was doing, not just a script that swung an arm on a timer. That meant the perception model had to be accurate enough to trust, fast enough to react in real time, robust enough to deploy at a public demo, and the surrounding ROS layer had to stay safe when individual components failed.

Figure: Robot Intelligence Systems Engineering V-Model showing requirement decomposition (left), integration build (centre), and verification closure (right) for RI-1 to RI-7.

Left Side of the V: Design Decomposition

Decomposition was performed by capability, not by codebase. RI-1 and RI-2 drove the real-time inference budget that shaped the dual-branch (voxel + pose) Transformer and the ~24 ms per-frame compute target. RI-3 drove the model architecture and the leave-one-person-out validation strategy. RI-4 drove the punch_processor sensor fusion logic and the pad-constraint filter. RI-5 drove every on-device deployment decision, from TensorRT FP16 conversion to the 16 GB shared-memory budget. RI-6 drove the sparring_engine, the Markov chain styles, and the persistent weakness profile. RI-7 drove the local Qwen2.5-3B LLM coach and its fallback tip system.

Base of the V: Integration Build

At the integration stage, all 10 ROS 2 nodes were wired together over 21 custom message types and 6 services, the trained CV model was packaged and deployed as a TensorRT engine on the Jetson, the Vue 3 + FastAPI dashboard was built and connected to the per-user SQLite database, and the LLM coach was loaded into shared GPU memory alongside the CV pipeline. The session_manager 5-state machine became the single source of truth that coordinated every other node, so all training modes (techniques, sparring, free, performance tests) flowed through the same lifecycle.

Right Side of the V: Verification Closure

Verification was planned from the same RI-1 to RI-7 requirements used during decomposition. The base of the testing pyramid is 146 pytest unit tests covering sensor fusion, gamification, and database operations. The middle layer is 28 cross-module integration tests that exercise ROS message contracts, fusion end-to-end, and motor protocol. The top is 12 system-level notebook sections plus the CDE AI Fair real-world deployment. Together these close the requirement-to-verification loop for all 7 RI requirements (see 5.3.4 Testing & Validation).

System Architecture

The entire system runs on an NVIDIA Jetson Orin NX using ROS 2 Humble (Robot Operating System 2), an industry-standard framework for building robotics software as a network of independent, communicating processes called nodes. ROS 2 was chosen because it provides reliable real-time messaging between components, allows each subsystem (CV, fusion, sparring, LLM) to be developed and tested independently, and is the standard for robotics projects requiring sensor integration and motor control.
