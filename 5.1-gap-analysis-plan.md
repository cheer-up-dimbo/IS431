## Summary of Gaps

5.3 establishes a rich backend that the GUI depends on as a consumer. The current 5.1 treats the integration as a black box ("via ROS 2" or "via a file-based handshake"). Several FYP template checklist items are also either missing or thin. The gaps fall into four categories:

1. **Interface contract with 5.3 is undocumented** — The GUI subscribes to 10 ROS signals and calls 3 services. None of these are named or mapped to GUI behaviors.
2. **Session orchestration role is implicit** — The GUI *initiates* and *terminates* sessions (StartSession / EndSession service calls). This is not stated anywhere in 5.1.
3. **IMU navigation and LLM coaching are mentioned but not documented** — Two significant design decisions are present only as brief mentions.
4. **Testing page is thin** — No mention of the pytest suite, no performance criteria table mapped to measured values, no CDE AI Fair user testing.
5. **Minor housekeeping** — Broken cross-reference ("5.4" should be "5.3").

### File 2: `pages/gui/implementation.html` (Implementation page)

#### Change 2a — Add "IMU Navigation" section (between ROS 2 Integration and Phone Dashboard)

**Content to add:**

The system supports hands-free navigation via the four IMU pads. This is a design requirement (GUI-1) but is not documented in the implementation. Key facts to cover:

- **Pad-to-action mapping:** Left pad = previous, Right pad = next, Centre pad = select/confirm, Head pad = back / toggle preset overlay on home screen.
- **Session-aware disable:** The `ImuNavHandler` tracks session state. When the session state is `countdown` or `active`, all nav commands are silently dropped to prevent accidental page changes from punch impacts. This is a deliberate safety design decision.
- **Keyboard fallback:** A `KeyboardNavFilter` event filter installed on the main window mirrors left/right/Enter/Escape for development without hardware.
- **Head pad special case on home:** On the home page, head pad toggles the preset overlay rather than navigating back, since there is no parent page to return to from home.

**Why this belongs in 5.1:** IMU navigation is a direct design response to a boxing-specific UX constraint (gloved hands). Its existence distinguishes this GUI from a generic touchscreen app. The mechanism is implemented entirely inside the GUI layer (`imu_nav_handler.py`) — it uses the ROS signal from `imu_node` (5.3) but the routing logic lives in 5.1.

#### Change 2b — Add "Session Orchestration" section (after IMU Navigation)

**Content to add:**

The GUI is the session lifecycle controller. Every training session — techniques, sparring, free training, or performance tests — is started and ended by explicit GUI service calls:

1. User taps "Start" → GUI calls `StartSession` service with mode, difficulty, config JSON, and username.
2. Session ID is returned → GUI holds this ID for the session duration.
3. Session state changes (`SESSION_STATE` topic) drive GUI timer, round counter, and rest screen transitions.
4. Session ends (timer expires, user stops early, or all rounds complete) → GUI calls `EndSession` with the session ID → receives a summary JSON that populates the post-session results page.

This contrasts with 5.3's perspective (which describes the `session_manager` node that *executes* the session). The GUI is the *initiator and terminator*; 5.3 is the *executor*.

**Why this belongs in 5.1:** Examiners need to understand which subsystem owns what. Without this, the division of responsibility between 5.1 and 5.3 is ambiguous.

#### Change 2c — Add "LLM Coaching Integration (GUI side)" section

**Content to add:**

The AI coaching features visible in the GUI are:

1. **In-session coaching tips:** A `COACH_TIP` ROS topic subscription delivers tips from 5.3's `llm_node`. When received, the `CoachTipBar` widget slides down from the top of the training page with a color-coded accent bar indicating tip type (technique, encouragement, correction, suggestion). The bar auto-collapses after 10 seconds to avoid obscuring the combo display.

2. **Post-session AI analysis:** After session end, the results page calls the `GenerateLlm` service with a prompt constructed from the session summary JSON. The response is displayed in a chat-style interface on the results page. If the LLM call fails or the model is unavailable, the GUI falls back to a hardcoded tip from the 54-entry fallback pool, selected by tip category.

3. **AI chat on phone dashboard:** The phone dashboard chat interface is backed by the same `GenerateLlm` service (routed through FastAPI on the 5.3 side). From the GUI's perspective this is transparent — it uses the same service client.

**Why this belongs in 5.1:** The coaching tip *display* and the *fallback behavior* are entirely implemented in the GUI layer. The LLM is 5.3's concern, but how coaching is surfaced to the user is 5.1's concern.

#### Change 2d — Add "Sound System" subsection (brief, under Key Engineering Decisions)

**Content to add:**

18 WAV sound effects are preloaded at startup by `SoundManager` into `QSoundEffect` objects for zero-latency playback. A priority tier system (1–5) prevents lower-priority sounds from masking higher-priority ones — for example, a round-start bell (priority 4) cannot be drowned out by a navigation tick (priority 1). Sounds are categorized: stimulus (5), bell (4), countdown (3), feedback (2), UI (1). Per-sound enable/disable toggles and master volume are configurable from the Settings page.

**Why this belongs in 5.1:** Sound is part of the sensory UX design and was a deliberate choice to reinforce session events (round bells, hit confirmation, countdown). It is entirely a 5.1 concern and is currently undocumented.

## What NOT to Add (Scope Boundaries)

- **CV model internals, TensorRT, action recognition pipeline** — these belong in 5.3.
- **FastAPI backend implementation, WebSocket protocol** — these belong in 5.3.3 (Dashboard & Analytics).
- **ROS node internals (session_manager, drill_manager, sparring_engine)** — these belong in 5.3.
- **Robot arm control mechanics** — these belong in 5.2.

The rule: if it lives in `boxbunny_core/` (ROS nodes), it's 5.3. If it lives in `boxbunny_gui/` or `boxbunny_dashboard/frontend/`, it's 5.1. The GuiBridge is the boundary — explaining *that it exists and what it carries* is 5.1; explaining what happens *inside the nodes after messages arrive* is 5.3.
